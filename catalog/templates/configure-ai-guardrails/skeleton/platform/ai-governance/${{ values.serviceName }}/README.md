# AI governance — ${{ values.serviceName }}

Generated by the **Configure AI Agent Guardrails** Backstage template. Two artifacts:

| File | What it is | How it is consumed |
| --- | --- | --- |
| `values.yaml` | Helm values overlay setting the harness env flags on the deployment | add to the service's Argo CD Application `valueFiles` |
| `governance.json` | OPA tenant data document (tool allow-list, code entitlement, grounding floor) | loaded by the OPA sidecar as `data.agent.tenants` |

## Wire the values overlay (one manual step)

Add this overlay after the base values in the service's Argo CD Application so it layers on top:

```yaml
# charts/${{ values.serviceName }} Application source
helm:
  valueFiles:
    - values.yaml
    - ../../platform/ai-governance/${{ values.serviceName }}/values.yaml
```

On merge, ArgoCD reconciles the deployment with the new env; the harness flags take effect with
no code redeploy.

## What is active now vs. forward-looking

- **Active now**: the on/off toggles and budget ceilings in `values.yaml` map to env the
  agent-service reads directly (`AGENT_TOOLS_POLICY_ENABLED`, `AGENT_GUARDRAIL_ENABLED`,
  `AGENT_BUDGET_*`) and the fail-open posture via `SPRING_APPLICATION_JSON`.
- **Forward-looking**: the per-tenant `allowed_tools` / `allow_code_execution` / `min_grounding`
  in `governance.json` are consumed by the `agent/tools` and `agent/io` Rego rules via
  `input.attributes` once `TenantId` is threaded end-to-end from the API (the documented
  follow-up in the agent-service `docs/agent-guardrails.md`). Until then they are carried as
  governance-as-code, versioned and reviewed in Git, ready to bind.
